# TMB public API — live audit of every documented endpoint

- Live-audit date: 2026-10-29 (server `DATA` field in responses reads `2026-10-28Z`).
- Base URL probed: `https://api.tmb.cat`, credentials sent as `app_id`/`app_key` query params on every call. Credential values are redacted everywhere in this document and in the capture metadata (`app_id=***&app_key=***`).
- Sources of truth for the path list: `docs/tmb-api/{transit,ibus,ibus_legacy,imetro,planner,static}.swagger.json` (Swagger 2.0, `basePath` per file) plus the non-`paths` forms inventoried in `docs/tmb-api/ENDPOINTS.md`, plus the alerts endpoints named in the task.
- Every body discussed below is stored verbatim in `captures-all/<slug>.json`; the slug is the `capture file` column.
- Counting: 53 live requests — 47 probes of documented endpoints (38 transit swagger `paths` + 3 transit path forms that only exist in prose in `ENDPOINTS.md` (`/linies/metro/{codi}`, `/linies/bus/{codi}`, `/parades/{codi}`) + 1 ibus + 2 ibus_legacy + 1 imetro + 1 planner + 1 static) + 2 alerts endpoints + 4 deliberate negative controls (metro `94`, bus `94`, bus `V15`, numeric `tipus`). Result: **50 × HTTP 200, 2 × HTTP 404, 1 × HTTP 403**. Six supplementary probes and the GTFS download were captured on top of that baseline (`transit_elements_superficie_corresp_dist1000.json`, `..._near_station_500.json`, `..._dist5000.json`, `transit_elements_superficie_near_station_500.json`, `extra_filter_CODI_LINIA_94.json`, `extra_srsName_EPSG25831_bus7_recs.json`, `gtfs-head.txt` + `gtfs.zip`).
- Real values used to fill path params: metro line `1` (L1) and `94` (L9N — `94` is the real `codi_linia` of L9N, see `captures-all/transit_linies_metro_94.json`); bus line `7` (there is no `V15` in the TMB dataset, see the vocabulary note below); station code `133` (La Sagrera, `codi_estacio` *and* `codi_estacio_linia`); station group `6660135` (Sant Andreu, `codi_grup_estacio`); access `13511` (Joan Torras, group scope) and `13301` (Meridiana | Hondures, line scope); bus stop `2259` (Diagonal - Llull); interchange `97` (Encants); `lon=2.17, lat=41.38, dist=300`; planner `fromPlace=41.3874,2.1700` → `toPlace=41.4036,2.1744`.
- Shape column: for GeoJSON, feature count and the set of live `geometry.type` values; for other payloads the top-level keys. Key-diff column compares the swagger 200-response schema against the first live feature/object, depth 3, `properties` flattened (`features.properties.X` shown as `X`); structural container keys and `crs.*` are omitted as noise. ## Broken or misdocumented endpoints

1. **`GET /v1/transit/elements/superficie/corresp/{lon}/{lat}/{dist}` is a dead branch — HTTP 200, always 0 features.** Four different inputs, four empty `FeatureCollection`s: `transit_elements_superficie_corresp.json` (2.17,41.38 / 300 m), `transit_elements_superficie_corresp_dist1000.json` (same point / 1000 m), `transit_elements_superficie_corresp_near_station_500.json` (La Sagrera station point / 500 m), `transit_elements_superficie_corresp_dist5000.json` (same point / 5 km). The sibling endpoint at the *same* point is not empty: `transit_elements_superficie_near_station_500.json` returns 36 features (22 `PARADES`, 8 `ACCESSOS`, 4 `ESTACIONS`, 2 `INTERCANVIADORS`) and `transit_elements_superficie.json` returns 6 features. So the near-point machinery works and only the `corresp` variant returns nothing; the response is a bare `{"type":"FeatureCollection","features":[]...}` of 133 bytes, not an error. The documented feature properties (`ID`, `CODI`, `CODI_TIPUS`, `NOM`, `NOM_TIPUS`, `PICTO`, `BEARING_IN_DEGREES`, `DISTANCE_IN_METERS`) could not be verified live at all.
2. **`{tipus}` in `/v1/transit/elements/superficie/{tipus}/{lon}/{lat}/{dist}` is a string enum, not a number.** The swagger enum is `ESTACIONS | PARADES | ACCESSOS | INTERCANVIADORS`; `PARADES` returns 200 with 5 features (`transit_elements_superficie_tipus_PARADES.json`), while the numeric form `2` endorsed by `docs/tmb-api/ENDPOINTS.md` returns **HTTP 404** with a gateway HTML body `Cannot GET /api/transit/elements/superficie/2/2.17/41.38/300` (`transit_elements_superficie_tipus_numeric_2.json`). `ENDPOINTS.md` is wrong here.
| 53 | `alerts_api_metro_web.json` | `/api/alerts/metro/channels/WEB` | 403 | 21 | plain text `Authentication failed` (not JSON, not HTML) | n/a (no JSON body) |
4. **`GET /v1/transit/linies/metro/{codi_linia}/trams` works and carries geometry.** HTTP 200, 31 features, every one a `MultiLineString` (`transit_linies_metro_trams.json`). `ENDPOINTS.md` states it was "reported live as HTTP 404, treat as removed/decommissioned" and that its `geometry` is unspecified; both statements are contradicted by this capture.
5. **`GET /v1/transit/linies/metro/{codi_linia}/horaris` returns `geometry: null`.** 5 features, all with a null `geometry` field (`transit_linies_metro_horaris.json`), while the schema builds every response on `FeatureBase`, which declares `geometry` as an object with `coordinates` and `type`. Clients that blindly dereference `feature.geometry.type` break on this endpoint and on the timetable records of `/linies/bus/7/horaris` (6 features, `MultiLineString`) — the two are inconsistent with each other too.

7. **Bus line codes are numeric-only in the TMB dataset, and the swagger types them as `number`.** `GET /v1/transit/linies/bus` returns 115 lines whose `CODI_LINIA` values are all numeric (`transit_linies_bus.json`); there is no `V15`, `H12` or `D20` in it, so `GET /v1/transit/linies/bus/V15` is a 404 (`transit_linies_bus_V15.json`). The vertical/horizontal/diagonal bus network is not served by this API. Note also that `codi_linia` being typed `number` in the spec is not a live constraint on metro: `94` is a *valid metro* code for L9N (`transit_linies_metro_94.json`) while `94` is simultaneously a valid *bus* code, a different line (`transit_linies_bus_94.json`) — the line code is only unique inside its mode.
8. **`ibus_legacy` line-scoped variant omits a documented field.** `GET /v1/ibus/stops/2259` returns items with `{destination, line, routeId, t-in-s, t-in-min, text-ca}` (`ibus_legacy_stops.json`) but `GET /v1/ibus/lines/7/stops/2259` returns items with the same shape **minus `line`** (`ibus_legacy_lines_stops.json`). A client that shares one parser across the two legacy endpoints gets a null/gap on the filtered one.
9. **`filter` is live but absent from the swagger.** `GET /v1/transit/linies/metro?filter=CODI_LINIA=94` returns exactly 1 feature (L9N) in 2 448 bytes (`extra_filter_CODI_LINIA_94.json`) versus 11 features unfiltered (`transit_linies_metro.json`). Only `srsName` appears in the spec (twice); `filter` appears nowhere in `transit.swagger.json`.
10. **Systematic schema drift on the transit entity properties.** Live payloads return `DATA` (a snapshot date, e.g. `2026-10-28Z`) on almost every feature and add `numberMatched`, `numberReturned` and `timeStamp` at the collection root; the spec instead documents `DATA_INICI` + `DATA_FI` (seeded validity window) and lacks all four live keys. Per-endpoint detail is in the table; the pattern repeats on `/estacions`, `/interc`, `/linies`, `/linies/bus`, `/linies/metro`, `/mobiliari`, `/parades` and their sub-resources.
11. **Several documented transit properties never appear live at all**, e.g. `ID` on `/elements/superficie*` and, on `/parades/{codi_parada}/mobiliari`, `ID_MOBILIARI`, `ID_MOB_PAR`, `ID_PARADA`, `NOM_MOBILIARI`, `DESC_MOBILIARI`, `ANGLE`, `DATA_INICI`, `DATA_FI` (`transit_parades_mobiliari.json`) — the endpoint answers 200 with 3 features whose only properties are stop-level fields. Treat the `properties` objects in the swagger as a superset, not a contract.

## Notes for app developers

- **Only three auth-free-failure shapes exist, and none is JSON.** A wrong/absent credential pair yields HTTP 401 on `/v1/transit/*` (observed while validating the credential wiring, before the audit run), a bad path yields 404 HTML `Cannot GET /api/...`, and `/api/*` yields 403 `Authentication failed`. Treat "200" as the only success signal and do not attempt to decode 4xx as JSON.
- **Response envelope:** every `/v1/transit/*` success is a GeoJSON `FeatureCollection` with `crs.properties.name = urn:ogc:def:crs:EPSG::4326` by default. `srsName=EPSG:25831` switches to projected metres — verified live: `extra_srsName_EPSG25831_bus7_recs.json` reports `urn:ogc:def:crs:EPSG::25831` and `[434432.41, 4584633.28]`, versus lon/lat in `transit_linies_bus_recs.json`.
- **`filter=<FIELD>=<value>` works server-side on list endpoints** and is the cheap way to avoid multi-hundred-KB downloads (`extra_filter_CODI_LINIA_94.json`), but it is undocumented in the swagger — pin a test if you rely on it.
- **Payload sizes that matter on mobile:** `/v1/transit/parades` 1 861 863 B (2 713 features), `/v1/transit/mobiliari` 930 232 B (3 179), `/v1/transit/linies` 702 908 B (162), `/v1/transit/linies/bus` 615 661 B (115), `/v1/transit/limits/municipis` 193 381 B (20 `MultiPolygon`s). Prefer the filtered or path-scoped variants: `/linies/metro` is 25 117 B for all 11 metro lines with full `MultiLineString` geometry (`transit_linies_metro.json`), and `/linies/metro/1/estacions` is 23 499 B for 30 stations (`transit_linies_metro_estacions.json`).
- **Geometry is not guaranteed.** In `/v1/transit/linies` (162 features) seven features have `geometry: null` — the FUNICULAR line and six `TREN` lines (R50, R60, L12, S3, S9, R8) — while every bus and metro line has `MultiLineString` (`transit_linies.json`). `/linies/metro/1/horaris` is entirely geometry-less (`transit_linies_metro_horaris.json`). Null-guard `feature.geometry`.
- **`/linies/metro/{codi}/recs` is the direction-aware polyline source you were looking for**: 2 features, both `MultiLineString` (`transit_linies_metro_recs.json`), versus the single per-line geometry from `/linies/metro`. Live properties are `SENTIT`, `CODI_FAMILIA`, `NOM_FAMILIA`, `ORDRE_FAMILIA`, `ORDRE_LINIA`, `ID_OPERADOR`, `NOM_OPERADOR`, `COLOR_REC`, `LONGITUD` — while the spec documents `CODI_SENTIT`, `CODI_SERVEI`, `ID_REC_LINIA`, `ID_TIPUS_SERVEI`, `DESC_SERVEI`, `ORIGEN_SERVEI`/`DESTI_SERVEI`, `DATA_INICI`/`DATA_FI`. Do not code against the spec names for this endpoint.
- **`/linies/bus/{codi}/recs` vs `/recs/cons` return identical bytes but different geometry types.** `transit_linies_bus_recs.json` and `transit_linies_bus_recs_reals.json` are both 7 705 B with `MultiLineString`; `transit_linies_bus_recs_cons.json` is 24 237 B with `LineString`. Pick the consolidated variant if your renderer expects a single ring per direction.
- **The GTFS feed does ship `shapes.txt` — the "TMB has no shapes" workaround is unnecessary.** `GET /v1/static/datasets/gtfs.zip` → HTTP 200, `content-type: application/zip`, `content-length: 8239824` (`gtfs-head.txt`; body saved as `gtfs.zip`). `unzip -l` lists 12 members: `feed_info.txt` 155 B, `agency.txt` 120 B, `routes.txt` 13 449 B, `stops.txt` 247 096 B, `transfers.txt` 1 129 B, **`shapes.txt` 3 721 675 B**, `trips.txt` 4 487 230 B, `calendar_dates.txt` 819 929 B, `calendar.txt` 177 B, `frequencies.txt` 166 B, `stop_times.txt` 58 755 449 B, `pathways.txt` 76 353 B. `shapes.txt` holds 102 401 data rows over 284 distinct `shape_id` values; `routes.txt` has 117 routes, 10 of them `route_type=1` (metro), and all 20 `shape_id`s referenced by metro trips are present in `shapes.txt`. ID convention is dotted: route `1.1.1` = L1, shape `1.1.100.1`; L9N is `1.94.1`.
- **Real-time feeds are structurally different from each other — do not share parsers.** `ibus` (`/v1/itransit/bus/parades/2259`) returns `{timestamp, parades[].linies_trajectes[].propers_busos[]}` with `temps_arribada` in epoch **ms** and an undocumented `info_bus.accessibilitat.estat_rampa` per bus (`ibus_bus_parades.json`); `imetro` (`/v1/itransit/metro/estacions?estacions=133`) returns `{timestamp, linies[].estacions[].linies_trajectes[].propers_trens[]}` keyed by `codi_via`/`id_sentit` (`imetro_metro_estacions.json`); `ibus_legacy` returns `{status, data:{ibus:[{routeId, line, t-in-s, t-in-min, text-ca}]}}` with relative seconds, no timestamp, and no epoch arithmetic needed (`ibus_legacy_stops.json`). The `imetro` and `ibus` schemas matched their swagger definitions with zero missing keys — they are the two most trustworthy specs in the set.
- **`estacions` is required and comma-separated on `imetro`.** Omitting it is the single most common integration failure; `estacions=133` (the La Sagrera `codi_estacio`) returns both directions of L1 with `propers_trens[].codi_servei` values `103`/`104`/`129`/`130` (`imetro_metro_estacions.json`).
